# Coffee Order System

## 1. 프로젝트 소개

다수의 서버·다수의 인스턴스 환경에서도 안정적으로 동작하는 커피숍 주문 시스템을 설계하고 구현하는 과제입니다.

핵심 기능은 아래와 같습니다.

- 커피 메뉴 목록 조회
- 포인트 충전
- 포인트 기반 커피 주문 및 결제
- 최근 7일 기준 인기 메뉴 조회
- 주문 내역의 실시간 외부 전송

이번 과제는 단순 CRUD 구현보다 아래 항목을 기술적으로 어떻게 해결할 것인지에 집중했습니다.

- 다중 서버, 다중 인스턴스 환경에서도 안정적으로 동작하는 구조
- 동시 요청 상황에서도 포인트와 주문 정합성을 보장하는 구조
- 주문 성공과 외부 이벤트 전송을 분리하는 비동기 처리 구조
- 최근 7일 인기 메뉴를 정확하게 집계하면서도 조회 성능을 고려한 구조

구현한 주요 기능은 아래와 같습니다.

- 커피 메뉴 목록 조회 API
- 포인트 충전 API
- 커피 주문/결제 API
- 인기 메뉴 조회 API
- 주문 이벤트 실시간 전송 구조

## 4. 도메인 설계 목표

이번 과제의 핵심 목표는 아래 4가지입니다.

1. 포인트 차감과 주문 생성은 항상 함께 성공하거나 함께 실패해야 한다.
2. 여러 서버 인스턴스에서 동시에 요청이 들어와도 같은 사용자 포인트 정합성이 깨지지 않아야 한다.
3. 외부 이벤트 전송 실패가 주문 실패로 전파되지 않아야 한다.
4. 인기 메뉴는 최근 7일 기준으로 정확하게 집계되어야 한다.

이를 만족하기 위해 아래 전략을 선택했습니다.

- 주문/결제: Redis 분산락 + DB 트랜잭션
- 포인트 충전: 낙관적 락
- 주문 이벤트 전송: Transactional Outbox + Kafka
- 인기 메뉴: 1차 DB 집계, 2차 Redis ZSET + Cache

## 5. 도메인 설계

### 도메인 엔티티

- `Member`
  - 사용자 식별 정보
- `PointWallet`
  - 현재 포인트 잔액 관리
- `PointHistory`
  - 포인트 충전/사용 이력 관리
- `CoffeeMenu`
  - 주문 가능한 메뉴 관리
- `CoffeeOrder`
  - 주문 및 결제 결과 저장
- `OrderOutbox`
  - 외부 전송용 주문 이벤트 저장
- `IdempotencyKey`
  - 주문 중복 요청 방지
- `OrderEventConsumeLog`
  - Kafka consumer 중복 소비 방지 로그

### 엔티티 관계

- `Member 1 : 1 PointWallet`
- `Member 1 : N PointHistory`
- `Member 1 : N CoffeeOrder`
- `CoffeeMenu 1 : N CoffeeOrder`
- `CoffeeOrder 1 : 1 OrderOutbox`

## 6. API 명세 요약

### 1) 커피 메뉴 목록 조회

- `GET /api/menus`
- 판매 가능한 메뉴 목록을 조회합니다.

### 2) 포인트 충전

- `POST /api/points/charge`
- 사용자 식별값과 충전 금액을 받아 포인트를 충전합니다.

요청 예시:

```json
{
  "memberId": 1,
  "amount": 10000
}
```

### 3) 커피 주문/결제

- `POST /api/orders`
- 사용자 식별값과 메뉴 ID를 받아 주문과 결제를 진행합니다.

요청 예시:

```json
{
  "memberId": 1,
  "menuId": 1,
  "idempotencyKey": "order-test-001"
}
```

### 4) 인기 메뉴 조회

- `GET /api/menus/popular`
- 최근 7일간 인기 메뉴 3개를 조회합니다.

## 7. 문제 해결 전략과 기술 선택 이유

### 7.1 주문/결제 정합성

주문은 아래 작업이 반드시 함께 처리되어야 합니다.

- 포인트 차감
- 주문 생성
- 포인트 사용 이력 저장
- Outbox 이벤트 저장

이를 위해 주문/결제는 하나의 DB 트랜잭션으로 처리했습니다.

### 7.2 동시성 제어

#### 포인트 충전

포인트 충전은 같은 사용자가 동시에 여러 번 충전할 가능성이 주문보다 낮다고 판단했습니다.
따라서 충전은 낙관적 락으로 처리했습니다.

선택 이유:

- 충돌 빈도가 상대적으로 낮음
- 충돌 시 재시도 메시지로 대응 가능
- 구현 복잡도를 과도하게 높이지 않아도 됨

선택하지 않은 방식:

- 비관적 락은 충돌이 드문 시나리오에서도 DB 락을 먼저 점유하게 되어 불필요하게 무거울 수 있다고 판단했습니다.
- 분산락도 적용 가능하지만, 충전은 주문보다 정합성 위험도가 낮아 현재 단계에서는 과하다고 판단했습니다.

문제점과 한계:

- 동시에 같은 사용자가 반복 충전하면 충돌 예외가 발생할 수 있음
- 재시도 정책이 없으면 사용자 경험이 다소 거칠 수 있음

대응 및 향후 계획:

- 현재는 예외 응답으로 명확히 실패를 알립니다.
- 향후 필요하면 재시도 정책이나 큐잉 전략을 추가할 수 있습니다.

#### 주문/결제

주문은 잔액 부족 판단과 차감이 매우 정확해야 하므로 더 강한 제어가 필요합니다.
주문은 Redis 분산락과 DB 트랜잭션을 함께 사용했습니다.

선택 이유:

- 다중 인스턴스 환경에서 사용자 단위 직렬화가 가능함
- DB 앞단에서 경합을 줄일 수 있음
- 최종 정합성은 DB 트랜잭션으로 보장 가능함

선택하지 않은 방식:

- DB 락만 사용하는 방식은 다중 서버 환경 설명력이 약하고, 모든 요청이 DB까지 진입한 뒤 경합하게 됩니다.
- Redis 분산락만 사용하는 방식은 최종 데이터 정합성을 보장하기에 부족하므로 트랜잭션과 함께 사용했습니다.

문제점과 한계:

- Redis 운영 복잡도가 추가됨
- 락 획득 실패나 대기 시간이 생길 수 있음
- 락과 트랜잭션을 함께 쓰므로 성능 튜닝 포인트가 늘어남

대응 및 향후 계획:

- 사용자 단위 락 키로 경합 범위를 최소화했습니다.
- 통합 테스트와 부하 테스트로 실제 직렬화 동작을 검증했습니다.
- 향후 락 대기 시간과 커넥션 풀 점유를 함께 관찰해 추가 튜닝할 예정입니다.

### 7.3 중복 주문 방지

주문 API는 `idempotencyKey`를 사용합니다.

선택 이유:

- 같은 요청이 네트워크 문제로 재전송되어도 중복 주문을 방지할 수 있음
- 실무에서 재시도가 가능한 주문 API에 자주 사용하는 패턴임

문제점과 한계:

- 키 저장 정책과 만료 정책을 함께 고려해야 함
- 클라이언트가 키를 일관되게 보내지 않으면 효과가 떨어짐

대응 및 향후 계획:

- 현재는 서버에서 키 중복 여부를 검증합니다.
- 향후 키 보관 기간 정책을 세분화할 수 있습니다.

### 7.4 외부 전송 실패 분리

주문 성공과 외부 이벤트 전송 성공을 하나로 묶지 않고 분리하기 위해 `Transactional Outbox Pattern`을 적용했습니다.

선택 이유:

- Kafka 또는 외부 전송 실패 때문에 주문 자체가 실패하면 안 됨
- DB 주문 데이터와 이벤트 저장의 정합성을 함께 보장할 수 있음
- 재시도 구조를 만들기 좋음

선택하지 않은 방식:

- 주문 트랜잭션 안에서 외부 시스템을 직접 호출하면 외부 장애가 내부 정합성 문제로 번질 수 있습니다.
- 단순 비동기 호출만 두면 주문은 성공했는데 이벤트가 저장조차 안 되는 구간이 생길 수 있습니다.

문제점과 한계:

- Outbox 테이블 관리 비용이 생김
- 폴링 또는 relay 운영이 필요함
- 재시도 정책과 상태 관리가 추가됨

대응 및 향후 계획:

- `PENDING`, `SENT`, `FAILED` 상태를 두고 재시도 구조를 만들었습니다.
- 향후 Outbox 정리 배치나 장기 보관 정책을 둘 예정입니다.

### 7.5 Kafka 선택 이유

Outbox 이벤트를 실제로 비동기 처리하기 위해 Kafka를 사용했습니다.

선택 이유:

- Producer와 Consumer를 분리할 수 있음
- 여러 Consumer Group으로 확장 가능
- 장애 복구 및 운영 관점에서 이벤트 스트림 구조를 설명하기 좋음
- 실시간 전송 요구사항을 충족하면서도 주문 트랜잭션과 외부 전송을 느슨하게 분리하기 좋음

이번 구현에서는 Kafka 전달 보장 방식을 `at-least-once` 기준으로 두었습니다.
이 방식을 선택한 이유는 주문 이벤트를 절대 잃지 않는 것이 한 번만 처리되게 만드는 것보다 더 우선이라고 판단했기 때문입니다.
메시지가 한 번 더 전달될 수는 있어도, 메시지가 유실되면 주문은 성공했는데 외부 수집 플랫폼에는 아예 전달되지 않는 문제가 생길 수 있습니다.

선택하지 않은 방식:

- `at-most-once`는 단순하지만 전송 실패 시 메시지 유실 가능성을 감수해야 하므로 주문 이벤트 성격과 맞지 않다고 판단했습니다.
- Kafka의 `exactly-once`는 매우 강력하지만 producer/consumer 설정, 트랜잭션 범위, 운영 복잡도가 커집니다. 과제 범위에서는 Kafka가 왜 필요한지와 중복 소비를 어떻게 제어하는지를 명확히 보여주는 쪽이 더 적절하다고 판단했습니다.

문제점과 한계:

- `at-least-once`는 중복 소비 가능성을 전제로 해야 함
- consumer 멱등 처리 전략이 반드시 필요함
- Kafka 운영과 모니터링 포인트가 늘어남

대응 및 향후 계획:

- 현재는 `at-least-once + consumer 멱등 처리` 조합을 선택했습니다.
- 중복 가능성은 `order_event_consume_log` 기반으로 제어합니다.
- 향후 운영 단계에서는 모니터링, DLT, 재처리 정책을 추가할 수 있습니다.

### 7.6 인기 메뉴 조회 전략

인기 메뉴는 최근 7일 기준 정확성이 우선이므로 1차 구현은 DB 집계를 사용했습니다.
이후 조회 성능 개선을 위해 Redis ZSET과 캐시를 추가했습니다.

선택 이유:

- 정답 소스를 DB로 둘 수 있음
- 반복 조회를 Redis로 빠르게 처리 가능함
- 정확성과 성능을 모두 설명하기 좋음

선택하지 않은 방식:

- 처음부터 ZSET만 정답 소스로 두면 최근 7일 조건과 데이터 정합성 설명이 복잡해질 수 있습니다.
- 단순 누적 랭킹은 최근 7일이라는 시간 조건을 정확히 반영하기 어렵습니다.

문제점과 한계:

- DB와 Redis를 함께 관리해야 함
- ZSET 키 전략과 캐시 무효화 정책이 필요함
- 집계 데이터 규모가 커지면 별도 최적화가 더 필요할 수 있음

대응 및 향후 계획:

- 현재는 DB를 정답 소스로 유지하고 Redis는 조회 최적화 용도로만 사용합니다.
- 일자별 ZSET과 짧은 TTL 캐시를 조합해 부하를 줄였습니다.

## 8. 주문 이벤트 처리 구조

### 8.1 전체 흐름

1. 주문 API 요청
2. 포인트 차감 + 주문 저장
3. Outbox 이벤트 저장
4. 트랜잭션 커밋
5. Outbox Relay가 Kafka로 발행
6. Kafka Consumer가 메시지를 수신
7. 소비 로그 저장으로 중복 소비 방지

### 8.2 Outbox + Kafka 구조를 선택한 이유

- 주문 데이터와 이벤트 저장의 정합성을 보장하기 위함
- 외부 메시지 전송 실패가 주문 실패로 전파되지 않게 하기 위함
- 이후 데이터 수집, 통계, 알림 등으로 확장하기 위함

### 8.3 Consumer 중복 방지

Kafka는 at-least-once 방식으로 운영될 수 있으므로 중복 소비 가능성을 고려해야 합니다.
이를 위해 `order_event_consume_log` 테이블을 두고, 이미 처리된 `orderId`는 다시 소비하지 않도록 구성했습니다.

장점:

- 구현 의도가 명확함
- 이미 처리한 주문인지 애플리케이션 레벨에서 직접 확인 가능함
- 과제 설명과 운영 관점 모두에서 설득력이 좋음

문제점과 한계:

- consume log 테이블이 계속 커질 수 있음
- 로그 저장 자체도 쓰기 비용이 추가됨
- 장기 운영 시 보관 정책이나 아카이빙 정책이 필요함

대응 및 향후 계획:

- 현재는 중복 처리 방지의 명확성을 우선했습니다.
- 이후 운영 단계에서는 기간 기준 정리 배치나 아카이빙 전략을 함께 둘 예정입니다.

## 9. 캐시 / Redis ZSET 전략

### 캐시 적용 대상

- 메뉴 목록 조회
- 인기 메뉴 조회

### 캐시 비적용 대상

- 사용자 포인트 잔액
- 주문 상태
- Outbox 상태

### 9.1 왜 메뉴 목록 조회를 캐시했는가

메뉴 목록은 대표적인 조회성 데이터라고 판단했습니다.

선택 이유:

- 메뉴 데이터는 주문이나 포인트처럼 초 단위로 계속 바뀌는 데이터가 아님
- 같은 목록을 여러 사용자가 반복 조회할 가능성이 높음
- 읽기 비용이 낮고 결과 구조도 단순함
- 캐시를 적용해도 결제 정합성 문제로 이어질 가능성이 낮음

선택하지 않은 방식:

- 매 요청마다 DB를 조회하는 것도 가능하지만, 동일한 조회가 반복되는 특성상 캐시 이점이 분명하다고 판단했습니다.

문제점과 한계:

- 캐시 무효화가 누락되면 오래된 메뉴가 보일 수 있음
- 메뉴 변경 빈도가 높아지면 TTL만으로는 부족할 수 있음

대응 및 향후 계획:

- 현재는 캐시 TTL을 짧게 두고, 변경 시 evict 가능한 구조로 유지했습니다.

### 9.2 왜 인기 메뉴 조회를 캐시했는가

인기 메뉴 조회는 최근 7일 조건이 포함된 집계 조회이기 때문에 메뉴 목록보다 DB 비용이 더 큰 조회입니다.

선택 이유:

- 단순 조건 조회가 아니라 집계와 정렬이 함께 들어감
- 메인 화면이나 추천 영역처럼 반복 조회 가능성이 높음
- 결과가 상위 3개 정도로 작아 캐시 효율이 좋음
- Redis ZSET과 짧은 TTL 캐시를 함께 사용하면 DB 집계 부담을 줄이기 좋음

선택하지 않은 방식:

- DB 집계만으로도 정답은 맞지만 반복 조회가 몰리면 집계 비용이 계속 발생합니다.
- ZSET만 정답 소스로 두는 방식은 최근 7일 정확성과 운영 복잡도 측면에서 아직 과하다고 판단했습니다.

문제점과 한계:

- 키 관리 복잡도가 증가함
- 7일 집계 합산 비용이 생김
- DB와 Redis 간 불일치 가능성을 항상 염두에 둬야 함

대응 및 향후 계획:

- DB를 기준 데이터로 유지합니다.
- Redis는 읽기 최적화 용도로만 사용합니다.
- 일자별 ZSET과 짧은 TTL 캐시를 조합했습니다.

### 9.3 왜 사용자 포인트 잔액은 캐시하지 않았는가

포인트 잔액은 이번 과제에서 가장 정합성이 중요한 상태 데이터입니다.

선택하지 않은 이유:

- 주문과 충전이 동시에 일어날 수 있어 최신성이 가장 중요함
- 오래된 캐시를 잘못 읽으면 잔액 부족 판단이나 차감 결과가 틀어질 수 있음
- 포인트는 조회 성능보다 쓰기와 검증의 정확성이 우선임
- 분산락, 트랜잭션, 잔액 검증 구조에 캐시가 섞이면 상태 동기화 복잡도가 커짐

문제점과 한계:

- 매번 DB를 보기 때문에 조회 비용은 더 큼

대응 및 향후 계획:

- 현재는 정합성을 우선해 DB 기준으로만 처리합니다.
- 향후 읽기 부하가 정말 커질 경우에도 포인트는 캐시보다 CQRS나 별도 조회 모델을 먼저 검토할 예정입니다.

### 9.4 왜 주문 상태는 캐시하지 않았는가

주문 상태는 결제 결과와 직접 연결되는 상태 데이터입니다.

선택하지 않은 이유:

- 주문 직후 `COMPLETED` 또는 실패 상태가 명확해야 함
- 취소, 재시도, 이벤트 전송 상태 연계 시 최신 상태 조회가 중요함
- 상태값이 잘못 캐시되면 사용자에게 잘못된 결과를 보여줄 수 있음

대응 및 향후 계획:

- 주문 상태는 DB 기준 조회를 유지합니다.

### 9.5 왜 Outbox 상태는 캐시하지 않았는가

Outbox는 단순 조회 데이터가 아니라 재시도와 운영 판단의 기준이 되는 운영 데이터입니다.

선택하지 않은 이유:

- `PENDING`, `SENT`, `FAILED` 상태 흐름이 중요함
- 재시도 시에는 최신 상태를 정확히 확인해야 함
- 오래된 캐시 상태는 운영 판단을 왜곡할 수 있음

대응 및 향후 계획:

- Outbox는 성능보다 운영 정확성을 우선해 DB 기준으로 처리합니다.

### 9.6 Redis ZSET 적용 방식

- 1차 구현: DB 집계
- 고도화: Redis ZSET + 인기 메뉴 캐시

Redis ZSET은 일자별 키를 사용합니다.

- 예: `popular:menu:20260720`

최근 7일 조회 시 7개 키를 기준으로 집계 결과를 만들고, 최종 결과 목록은 별도 캐시로 재사용합니다.

## 10. 주요 트레이드오프

이번 설계는 모든 영역에서 가장 강한 기술만 쓰기보다, 과제 범위에서 설명 가능하고 검증 가능한 균형점을 찾는 방향으로 결정했습니다.

### 10.1 주문 동시성 제어

- 선택: `Redis 분산락 + DB 트랜잭션`
- 장점:
  - 다중 인스턴스 환경에서 같은 사용자 요청을 공통 기준으로 직렬화할 수 있습니다.
  - 최종 정합성은 DB 트랜잭션으로 보장할 수 있습니다.
- 단점:
  - Redis 운영 복잡도가 추가됩니다.
  - 락 실패와 대기 시간이 생길 수 있습니다.
- 판단 이유:
  - 단순 DB 락만으로는 다중 서버 환경 설명력이 부족했고, 주문/결제 정합성이 가장 중요하다고 판단했습니다.

### 10.2 포인트 충전 락 전략

- 선택: `낙관적 락`
- 장점:
  - 충돌이 적은 시나리오에서 성능이 유리합니다.
  - 구현 복잡도를 과도하게 높이지 않을 수 있습니다.
- 단점:
  - 충돌 발생 시 재시도나 실패 응답 처리가 필요합니다.
- 판단 이유:
  - 충전은 주문보다 경합 가능성이 낮고, 실패 후 다시 시도하는 UX가 상대적으로 자연스럽다고 판단했습니다.

### 10.3 주문 이벤트 전송

- 선택: `Transactional Outbox + Kafka`
- 장점:
  - 주문 DB 저장과 이벤트 저장의 정합성을 함께 보장할 수 있습니다.
  - 외부 전송 실패가 주문 실패로 전파되지 않습니다.
  - Producer / Consumer 분리와 확장성이 좋습니다.
- 단점:
  - 구조가 단순 HTTP 호출보다 복잡합니다.
  - Outbox 관리, Kafka 운영, Consumer 멱등 처리까지 고려해야 합니다.
- 판단 이유:
  - 과제의 실시간 전송 요구사항을 정합성과 함께 설명하려면 Outbox + Kafka 조합이 가장 설득력 있다고 봤습니다.

### 10.4 인기 메뉴 조회

- 선택: `1차 DB 집계 + 2차 Redis ZSET/Cache`
- 장점:
  - 최근 7일 조건을 정확하게 처리할 수 있습니다.
  - 조회 트래픽이 커질수록 Redis 최적화 효과를 설명할 수 있습니다.
- 단점:
  - DB와 Redis를 함께 관리해야 합니다.
  - ZSET 키 전략과 캐시 무효화 정책이 추가로 필요합니다.
- 판단 이유:
  - 과제 초반에는 정확성이 우선이고, 이후 고도화에서 성능 개선 방향도 함께 보여줄 수 있다고 판단했습니다.

### 10.5 Kafka Consumer 중복 방지

- 선택: `order_event_consume_log` 기반 중복 소비 방지
- 장점:
  - at-least-once 소비 환경에서 같은 주문 이벤트 중복 처리를 막을 수 있습니다.
  - 실제 운영 중 소비 이력 추적도 가능합니다.
- 단점:
  - 로그 테이블이 계속 증가할 수 있습니다.
  - 저장 비용과 정리 정책이 필요합니다.
- 판단 이유:
  - 과제 범위에서는 exactly-once 자체를 과하게 끌어가기보다, 멱등 처리 구조를 명확히 보여주는 편이 더 현실적이라고 판단했습니다.

## 11. 인덱싱 전략

적용한 주요 인덱스는 아래와 같습니다.

- `coffee_order(status, ordered_at, menu_id)`
- `coffee_order(member_id, ordered_at)`
- `order_outbox(status, created_at)`
- `point_wallet(member_id)`

이유:

- 인기 메뉴 집계
- 회원 주문 이력 조회
- Outbox 재시도 조회
- 포인트 지갑 단건 조회

이번 인덱싱은 일단 많이 추가하는 방식이 아니라, 실제 조회 패턴이 분명한 컬럼에만 최소한으로 적용하는 방향으로 잡았습니다.
이유는 인덱스가 많아질수록 조회는 빨라질 수 있지만, 반대로 주문 저장, 포인트 변경, 아웃박스 저장 같은 쓰기 비용이 커지기 때문입니다.

각 인덱스를 선택한 이유는 다음과 같습니다.

- `coffee_order(status, ordered_at, menu_id)`는 최근 7일 완료 주문을 기준으로 인기 메뉴를 집계할 때 사용하는 조건을 맞추기 위해 추가했습니다.
- `coffee_order(member_id, ordered_at)`는 회원별 주문 이력 조회나 향후 사용자 주문 분석 확장 가능성을 고려해 추가했습니다.
- `order_outbox(status, created_at)`는 `PENDING` 상태 이벤트를 생성 순서대로 빠르게 찾아 재시도하기 위해 추가했습니다.
- `point_wallet(member_id)`는 회원 기준 지갑 단건 조회가 매우 자주 발생하므로 빠른 탐색을 보장하기 위해 추가했습니다.

선택하지 않은 방식:

- 모든 조건마다 인덱스를 넓게 추가하는 방식은 쓰기 성능 저하와 관리 복잡도 증가 가능성이 커서 지양했습니다.
- 조회 쿼리를 먼저 QueryDSL이나 복잡한 튜닝으로 푸는 방식보다, 현재 요구사항에서는 인덱스 설계와 실행 계획 검증이 더 직접적이고 설명 가능성이 높다고 판단했습니다.

문제점과 한계:

- 복합 인덱스가 모든 `group by`, `order by`, 범위 조건을 완벽하게 해결하지는 못합니다.
- 인기 메뉴처럼 집계가 들어가는 쿼리는 인덱스가 있어도 데이터가 크게 늘면 결국 집계 비용이 커질 수 있습니다.
- 인덱스가 늘수록 insert/update 비용이 증가합니다.

대응 및 향후 계획:

- 현재는 `EXPLAIN`으로 실제 `key` 사용 여부를 확인했습니다.
- `SHOW INDEX`와 `EXPLAIN`으로 인덱스가 기대한 쿼리에서 실제로 사용되는지 검증했습니다.
- 향후 데이터 규모가 커지면 인기 메뉴 집계 전용 읽기 최적화 구조, 아웃박스 히스토리 분리 또는 파티셔닝, 조회 패턴 변화에 따른 인덱스 재조정을 검토할 예정입니다.

실행 계획 검증 문서는 아래에 정리했습니다.

- [docs/performance/INDEXING_AND_EXPLAIN.md](docs/performance/INDEXING_AND_EXPLAIN.md)

### 11.1 QueryDSL TODO

현재 코드는 QueryDSL을 사용하지 않고 JPA Repository와 JPQL 기반으로 구현했습니다.
현재 단계에서 QueryDSL을 바로 도입하지 않은 이유는, 과제의 핵심 요구사항을 충족하는 데 필요한 조회가 아직 복잡한 동적 검색 수준까지는 아니었기 때문입니다.
특히 인기 메뉴 조회는 조건이 고정되어 있어 JPQL로도 충분히 의도를 드러낼 수 있다고 판단했습니다.

선택하지 않은 이유:

- 현재 요구사항 기준으로는 도입 비용 대비 체감 이점이 크지 않았음
- 빌드 설정, QClass 관리, 레이어 분리까지 함께 늘어나므로 과제 초반 구현 속도를 떨어뜨릴 수 있음
- 지금 단계에서는 인덱스와 실행 계획 검증이 더 우선순위가 높다고 판단했음

언제 추가하면 좋은가:

- 관리자 검색 조건이 늘어날 때
- 주문 이력 필터가 날짜, 상태, 회원, 메뉴 등으로 복잡해질 때
- 인기 메뉴 집계 조건이 기간, 상태, 그룹 기준으로 더 동적으로 확장될 때

향후 계획:

- 단순 조회는 JPA/JPQL 유지
- 복잡한 동적 검색부터 QueryDSL로 분리
- Custom Repository 계층으로 확장

## 12. 성능 검증 결과

성능 검증 도구는 `k6`를 선택했습니다.
선택 이유는 스크립트 기반으로 시나리오를 명확하게 남길 수 있고, 일반 부하, 한계, 급상승, 내구성 테스트를 한 파일 안에서 재현하기 좋으며, 과제 제출 시 어떤 부하를 어떤 기준으로 검증했는지 설명하기에도 적합했기 때문입니다.
또한 Postman 컬렉션 기반 확인보다 동시 사용자 수, 지속 시간, 임계치(threshold)를 구조적으로 선언할 수 있어 동시성, 락 경합, 응답 시간 검증에 더 잘 맞는다고 판단했습니다.

### 12.1 일반 부하 테스트

목적:

- 평상시 또는 예측 가능한 혼잡 구간에서 안정적으로 동작하는지 확인

기준:

- 동시 사용자 50~100명 수준

이유:

- 과제 규모에서 현실적인 혼잡 상황을 재현하기 적절함
- 전국 단위 또는 하나의 회사 조직, 건물, 캠퍼스, 또는 특정 그룹 사용자가 평시 이용하는 수준을 기준으로 잡았음
- 너무 낮으면 병목이 드러나지 않고, 너무 높으면 인프라 한계만 먼저 보일 수 있음
- 주문 API, 락 대기, DB 커넥션 풀 반응을 보기 위한 초기 기준치로 적절함

### 12.2 한계 테스트

목적:

- 어느 지점부터 에러율이 증가하는지 확인

방식:

- 사용자 수를 점진적으로 증가시키며 병목 지점을 탐색

선택 이유:

- 단순 성공 여부보다 시스템이 무너지기 시작하는 구간을 확인하는 것이 중요하다고 판단했음
- 주문 API, Redis 락, DB 커넥션 풀, Kafka relay 중 어디서 먼저 병목이 나는지 구간별로 보기 좋음
- 이후 튜닝 전후 비교 기준점으로 활용하기 좋음

### 12.3 급상승 테스트

목적:

- 짧은 시간에 요청이 급증할 때 안정적인지 확인

기준:

- 동시 사용자 10명에서 200명까지 급격히 증가

이유:

- 특정 시점에 주문이 몰리는 상황을 가정하기 위함
- 특정 시점은 출근 직후, 점심 직전, 쉬는 시간처럼 몰리는 시간대
- 락 경합, 커넥션 풀 고갈, Kafka 적체, 응답 시간 급증 같은 병목을 빠르게 드러내기 위함
- 시스템의 회복력과 피크 대응 능력을 보기 위함

선택 이유:

- 평균 부하만으로는 순간 피크 상황에서의 취약점을 확인하기 어려움
- 분산락과 트랜잭션 구조는 순간 경합이 커질 때 특성이 더 잘 드러남
- 과제 환경에서도 현실적으로 재현 가능한 피크 시나리오라고 판단했음

### 12.4 내구성 테스트

목적:

- 장시간 실행 시 자원 누수나 성능 저하 확인

방식:

- 30분~1시간 이상 지속 요청
- 응답 시간 증가, 메모리 사용량, 커넥션 풀 상태 관찰

선택 이유:

- 짧은 테스트에서는 드러나지 않는 누적형 문제를 확인하기 위함
- 캐시, 락, Kafka, DB 커넥션이 함께 동작할 때 시간이 지날수록 문제가 생기는지 보기 위함
- 실무에서는 순간 성능뿐 아니라 시간이 지나도 안정적인지가 중요하다고 판단했음

### 12.5 포인트 충전 API 결과

- 최대 `200 VU`
- `p95 = 216.79ms`
- `p99 = 649.97ms`
- 실패율 `0.04%`

### 12.6 주문/결제 API 결과

초기에는 테스트 시나리오 문제로 실패율이 높게 측정되었습니다.
이후 `사전 충전 + 여러 회원 분산 + 충전 성공 회원만 사용` 방식으로 시나리오를 보정했습니다.

이렇게 보정한 이유는 주문 API의 진짜 병목을 보고 싶었기 때문입니다.
포인트가 없는 동일 회원에게 주문을 몰아 보내면, 주문 비즈니스 로직 성능보다 잔액 부족 예외가 결과를 더 크게 왜곡할 수 있습니다.
그래서 실제 주문 트래픽에 가깝게 여러 회원이 사전 충전된 상태에서 동시에 주문하는 흐름으로 조정했습니다.

보정 후 결과:

- 최대 `200 VU`
- `p95 = 229.95ms`
- `p99 = 652.42ms`
- 실패율 `0.00%`

### 12.7 인기 메뉴 조회 API 결과

- 최대 `400 VU`
- `p95 = 5.74ms`
- `p99 = 8.23ms`
- 실패율 `0.00%`

### 12.8 혼합 부하 테스트

주문/결제 API와 인기 메뉴 조회 API를 동시에 실행해 읽기/쓰기 혼합 상황을 검증했습니다.

- 주문 API 혼합 부하 `p95 = 223.15ms`, 실패율 `0.00%`
- 인기 메뉴 혼합 부하 `p95 = 12.41ms`, 실패율 `0.00%`

## 13. 테스트 전략

### 단위 테스트

- 메뉴 조회 서비스 테스트
- 포인트 충전 서비스 테스트
- 주문 서비스 테스트
- Outbox Relay 테스트
- Kafka Producer 테스트
- Kafka Consumer 서비스 테스트
- Kafka Listener Ack 테스트

단위 테스트는 정책과 분기를 빠르게 검증하기 위해 작성했습니다.
서비스 단위에서 예외 처리, 잔액 검증, 중복 주문 방지, Outbox 저장, Kafka 발행 호출 여부처럼 비즈니스 규칙을 빠르게 확인하는 데 집중했습니다.
또한 외부 인프라 영향을 줄이기 위해 Mockito 기반 mock 테스트를 적극 사용했습니다.

### 동시성 / 통합 테스트

- 포인트 분산락 테스트
- 주문 분산락 테스트

통합 테스트는 단위 테스트만으로는 검증하기 어려운 락, 트랜잭션, Redis 연동 같은 실제 협업 지점을 확인하기 위해 분리했습니다.
특히 분산락은 메서드가 호출되었다보다 실제로 동시에 요청했을 때 하나씩 직렬화되는지가 중요하므로 통합 테스트가 더 적합하다고 판단했습니다.

### 성능 테스트

- k6 기반 부하 테스트
- 일반 부하
- 한계 테스트
- 급상승 테스트
- 내구성 테스트

성능 테스트는 기능 성공 여부가 아니라, 동시 요청이 늘어났을 때 응답 시간과 실패율이 어떻게 변하는지를 보기 위한 용도입니다.
즉 단위 테스트는 맞게 동작하는가, 통합 테스트는 함께 붙였을 때도 맞는가, 성능 테스트는 부하가 커져도 버티는가를 각각 확인하는 역할로 나누었습니다.

## 14. HikariCP Connection Pool TODO

주문/결제 API는 락과 트랜잭션을 함께 사용하므로, 실제 트래픽이 커질수록 DB 커넥션 풀이 병목이 될 가능성이 있습니다.
이번 과제에서는 정합성 보장과 동시성 제어 구조를 먼저 안정화하는 것을 우선순위로 두었고, HikariCP 자체 튜닝은 후속 최적화 항목으로 남겼습니다.

향후 이 작업을 진행하면 좋은 점은 다음과 같습니다.

- 락 대기 상황에서 커넥션 점유 시간이 얼마나 늘어나는지 더 정확하게 확인할 수 있음
- 최대 동시 주문 수 대비 적절한 풀 크기를 찾을 수 있음
- DB가 버티는 범위와 애플리케이션이 버티는 범위를 분리해서 볼 수 있음

반대로 문제점과 한계도 있습니다.

- 로컬 환경에서는 애플리케이션 병목과 PC 자원 한계가 섞여 보여 해석이 어려울 수 있음
- 풀 크기를 무작정 키우면 DB 부하가 더 커질 수 있음
- 커넥션 풀만 조정해도 락 경합 자체가 사라지는 것은 아님

그래서 향후에는 다음 순서로 확인할 예정입니다.

- 주문 API 부하 테스트 중 active connection, pending acquisition 관찰
- DB 응답 시간과 애플리케이션 응답 시간 함께 비교
- 락 대기 증가 시 풀 크기 조정 전후 결과 비교
- 필요 시 읽기/쓰기 트래픽 분리 전략 검토
