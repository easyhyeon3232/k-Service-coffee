# Coffee Order System

## 1. 프로젝트 소개

다수의 서버·다수의 인스턴스 환경에서도 안정적으로 동작하는 커피숍 주문 시스템을 설계하고 구현하는 과제입니다.

핵심 기능은 아래와 같습니다.

- 커피 메뉴 목록 조회
- 포인트 충전
- 포인트 기반 커피 주문 및 결제
- 최근 7일 기준 인기 메뉴 조회
- 주문 내역의 실시간 외부 전송

이번 과제는 단순 CRUD 구현보다 아래 항목을 기술적으로 어떻게 해결할 것인지에 집중했습니다.

- 다중 서버·다중 인스턴스 환경에서도 안정적으로 동작하는 구조
- 동시 요청 상황에서도 포인트와 주문 데이터의 정합성 보장
- 주문 성공과 외부 데이터 플랫폼 전송 성공을 분리한 안정적인 이벤트 처리
- 최근 7일 인기 메뉴를 정확하게 집계할 수 있는 조회 구조
- 테스트와 부하 검증을 통해 설계가 실제로 안전한지 증명

## 4. 핵심 설계 목표

이번 과제는 주문/결제 성격의 시스템이기 때문에 성능보다 먼저 정합성과 안정성을 보장해야 한다고 판단했습니다.

핵심 목표는 아래와 같습니다.

- 포인트 잔액이 음수가 되지 않도록 보장한다.
- 주문 생성과 포인트 차감이 항상 함께 성공하거나 함께 실패하도록 만든다.
- 외부 시스템 장애가 주문 실패로 전파되지 않도록 분리한다.
- 인기 메뉴 집계 결과가 최근 7일의 실제 주문 데이터와 일치하도록 한다.
- 여러 서버 인스턴스가 동시에 실행되어도 동일한 결과를 보장한다.

## 5. 동시성 제어 전략

### 5.1 문제 정의

가장 중요한 경쟁 자원은 `사용자 포인트 잔액`입니다.

동시에 아래 상황이 발생할 수 있습니다.

- 같은 사용자가 여러 번 주문 요청
- 충전과 주문이 동시에 발생
- 여러 서버 인스턴스가 같은 사용자 잔액을 동시에 수정

잘못 처리되면 아래 문제가 발생할 수 있습니다.

- 잔액보다 많은 금액이 차감됨
- 충전과 차감 순서가 꼬여 최종 잔액이 틀어짐
- 서버가 여러 대일 때 인스턴스별로 다른 결과가 나옴

### 5.2 왜 비관적 락을 선택하지 않았는가

비관적 락은 정합성 측면에서는 강력하지만, 이번 과제에서는 최종 선택지로 두지 않았습니다.

이유는 아래와 같습니다.

- DB 레벨 락이므로 여러 인스턴스 환경에서도 동작은 가능하지만, 락 대기 시간이 길어지면 DB 커넥션 점유 시간이 함께 증가함
- 주문 트래픽이 몰리면 DB 자체가 병목이 될 가능성이 큼
- 락 경합이 많을수록 처리량이 급격히 떨어질 수 있음
- 이번 과제는 `다중 서버 환경에서의 확장성`도 설명해야 하므로, 애플리케이션 외부에서 공통으로 관리되는 락이 더 설계 의도를 드러내기 좋다고 판단함

즉, 비관적 락은 안정적이지만 `DB 부담 증가`와 `확장성 한계`가 분명하다고 보았습니다.

### 5.3 왜 낙관적 락을 선택하지 않았는가

낙관적 락은 충돌이 적은 환경에서는 효율적이지만, 이번 과제의 주문/결제 성격과는 다소 맞지 않는다고 판단했습니다.

이유는 아래와 같습니다.

- 포인트 차감은 충돌이 실제로 자주 발생할 수 있는 영역임
- 충돌이 발생하면 재시도 로직이 필수인데, 사용자 요청 단에서 재시도 정책까지 설계해야 함
- 주문/결제는 실패보다 정확한 한 번 처리가 더 중요함
- 낙관적 락은 충돌 후 실패/재시도 흐름을 설명해야 해서 과제에서 논리가 더 복잡해짐

즉, 낙관적 락은 성능상 장점은 있지만 이번 과제에서는 `충돌 가능성이 높은 자원`이라 우선순위가 낮다고 보았습니다.

### 5.4 왜 Redis 원자 연산만으로 처리하지 않았는가

Redis의 `INCR`, `DECR`, Lua Script 같은 원자 연산도 고려할 수 있지만, 이번 과제에서는 핵심 해법으로 선택하지 않았습니다.

이유는 아래와 같습니다.

- 주문은 단순히 포인트 숫자만 줄이는 작업이 아님
- 포인트 차감과 동시에 주문 생성, 결제 성공 처리, 외부 전송 이벤트 저장까지 함께 일어나야 함
- Redis 원자 연산은 숫자 변경에는 강하지만, `DB 주문 데이터와 함께 하나의 비즈니스 트랜잭션`으로 묶기는 어려움
- Redis와 DB를 완전한 하나의 원자적 트랜잭션처럼 다루기 어렵기 때문에, 중간 실패 시 정합성 문제가 생길 수 있음

즉, 포인트 차감만 보면 원자 연산이 매력적이지만, 이번 과제의 핵심은 `주문 + 결제 + 이벤트 저장의 일관성`이기 때문에 단독 해법으로는 부족하다고 판단했습니다.

### 5.5 왜 분산락을 선택했는가

이번 과제에서는 `Redis 기반 분산락(Redisson)`을 중심으로 동시성 제어를 설계하려고 합니다.

선택 이유는 아래와 같습니다.

- 다중 서버·다중 인스턴스 환경에서 공통 락 자원을 사용할 수 있음
- 같은 사용자에 대한 주문/충전 요청을 서버 수와 무관하게 직렬화할 수 있음
- DB 락보다 앞단에서 경쟁을 줄여 DB 부담을 완화할 수 있음
- 과제 요구사항인 여러 서버 환경에서도 동일하게 동작하는 구조를 설명하기 좋음

즉, 분산락은 `여러 서버가 동시에 접근하는 상황을 제어하기 위한 공통 게이트`로 사용하고, 실제 데이터 정합성은 DB 트랜잭션으로 보장하는 이중 안전장치 구조를 가져가려고 합니다.

### 5.6 적용 방식

락 키는 사용자 단위로 관리합니다.

- `point:user:{userId}`

주문 요청 처리 순서는 아래와 같습니다.

1. 사용자 포인트 락 획득
2. 트랜잭션 시작
3. 포인트 잔액 조회
4. 잔액 검증
5. 포인트 차감
6. 주문 생성
7. Outbox 이벤트 저장
8. 트랜잭션 커밋
9. 락 해제

즉, 분산락은 여러 서버 간 동시 접근 제어, 트랜잭션은 DB 정합성 보장 역할로 분리해 사용합니다.

## 6. Redis 고가용성 구조

### 6.1 왜 단일 노드로 두지 않는가

분산락을 Redis에 의존하는 순간 Redis 장애가 전체 주문 처리의 단일 장애점이 될 수 있습니다.

따라서 Redis를 단일 인스턴스로만 두는 것은 위험하다고 판단했습니다.

### 6.2 고려하는 구조

Redis는 아래 방향으로 고가용성을 고려합니다.

- `Master` 1대
- `Replica` 1대 이상
- `Sentinel` 또는 운영 환경에서는 관리형 Redis 사용 고려

역할은 아래처럼 나눕니다.

- `Master`: 쓰기, 락 처리
- `Replica`: 조회 트래픽 분산

다만 분산락은 일관성이 더 중요하므로, 락 관련 처리는 쓰기 노드 기준으로 처리합니다.

### 6.3 왜 Master/Replica 구조를 고려하는가

- 조회 트래픽을 Replica로 분산 가능
- Master 장애 시 failover 구조를 고려할 수 있음
- 메뉴 캐시, 인기 메뉴 캐시 같은 읽기성 데이터는 Replica 활용 여지가 있음

주의할 점은 아래와 같습니다.

- 분산락은 복제 지연 문제가 있으면 위험할 수 있음
- 락은 Redisson과 적절한 Redis 구성 위에서 신중히 사용해야 함
- 락 일관성이 중요한 구간은 쓰기 노드 기준으로 처리해야 함

## 7. Kafka를 사용하는 이유

### 7.1 왜 Kafka가 필요한가

주문 내역을 데이터 수집 플랫폼으로 실시간 전송해야 하는데, 이 전송이 주문 API 응답 흐름과 강하게 결합되면 아래 문제가 생깁니다.

- 외부 시스템 장애가 주문 실패로 전파됨
- 외부 API 지연이 주문 응답 지연으로 이어짐
- 재시도, 병렬 처리, 장애 격리 구조가 약해짐

Kafka를 사용하면 주문 시스템과 후속 처리 시스템을 느슨하게 분리할 수 있습니다.

### 7.2 Kafka만의 장점

Kafka를 고려하는 가장 큰 이유는 아래와 같습니다.

- 이벤트를 안전하게 버퍼링할 수 있음
- producer와 consumer를 분리할 수 있음
- 하나의 이벤트를 여러 consumer group이 각자 병렬로 처리할 수 있음
- 실시간 전송 + 비동기 처리 + 장애 내성을 함께 설명하기 좋음
- 고가용성 클러스터 구조로 방어 가능함

특히 하나의 주문 이벤트를 여러 소비자가 각자 다르게 처리할 수 있다는 점이 중요합니다.

예시:

- 데이터 수집 플랫폼 전송 consumer
- 인기 메뉴 집계 consumer
- 로그/감사 이벤트 저장 consumer

이 구조는 단순 retry queue보다 확장성과 병렬성 측면에서 더 유리합니다.

### 7.3 왜 단순 Retry Queue만으로는 부족한가

- retry queue는 보통 실패 복구에 초점이 있음
- Kafka는 실패 복구뿐 아니라 `이벤트 스트림 기반의 병렬 소비 구조`를 제공함
- 같은 이벤트를 여러 consumer group이 독립적으로 읽을 수 있어 확장성이 좋음
- 내구성, 파티셔닝, consumer group 기반 확장 같은 특성이 있음

즉, Kafka는 단순 재시도 도구가 아니라 `이벤트 중심 아키텍처`를 가능하게 해주는 메시징 플랫폼으로 보았습니다.

## 8. Outbox + Kafka 전략

### 8.1 왜 Outbox를 함께 쓰는가

Kafka를 바로 발행하는 것만으로는 DB 주문 저장과 메시지 발행의 원자성을 보장하기 어렵습니다.

예를 들면 아래 문제가 생길 수 있습니다.

- 주문은 DB에 저장됐는데 Kafka 발행 실패
- Kafka는 발행됐는데 DB 주문 저장 실패

그래서 `Transactional Outbox`를 함께 사용합니다.

### 8.2 적용 방식

주문 트랜잭션 안에서 아래를 함께 처리합니다.

- 포인트 차감
- 주문 저장
- Outbox 이벤트 저장

그 후 별도 Publisher가 Outbox를 읽어 Kafka로 발행합니다.

### 8.3 트레이드오프

장점:

- DB와 이벤트 저장의 정합성 보장
- 외부 장애가 주문 실패로 전파되지 않음
- 재시도 정책 적용 가능

단점:

- Outbox polling 지연이 존재함
- 테이블 관리 비용이 생김
- 중복 발행 가능성 고려 필요

대응:

- consumer 멱등 처리
- retry 횟수 관리
- 오래된 Outbox 데이터 정리 배치
- 추후 CDC 기반 확장 가능성 검토

## 9. Kafka 전송 보장 방식과 DLT 전략

### 9.1 전송 보장 방식

이번 과제에서는 `At-least-once + 멱등 처리` 전략을 선택하려고 합니다.

이유는 아래와 같습니다.

- 유실 방지가 가장 중요함
- Exactly-once는 과제 범위 대비 복잡도가 높음
- 중복은 consumer 멱등성으로 완화 가능함

### 9.2 DLT 전략

처리 실패 메시지는 무한 재시도하지 않고 DLT로 보냅니다.

정책은 아래와 같습니다.

- 일시적 장애: 제한 횟수 재시도
- 재시도 초과: DLT 이동
- 데이터 오류, 스키마 오류: 빠르게 DLT 격리

DLT에는 아래 정보를 남깁니다.

- 원본 payload
- 실패 사유
- retry 횟수
- 발생 시각

## 10. 인기 메뉴 전략과 Redis ZSET 활용 방향

### 10.1 기본 전략

초기 구현은 `DB 집계`로 가져가려고 합니다.

이유는 아래와 같습니다.

- 최근 7일 조건을 가장 정확하게 처리 가능
- 정답 소스를 DB로 두는 것이 안전함
- 제출용 과제에서는 정확성이 성능보다 우선

### 10.2 Redis ZSET을 고려하는 이유

배운 기술 중 `Redis ZSET`은 인기 메뉴와 랭킹 문제에 잘 맞기 때문에 확장 설계로 반영하려고 합니다.

ZSET을 고려하는 이유는 아래와 같습니다.

- score 기반 정렬이 가능함
- top N 조회가 빠름
- 실시간 랭킹 처리에 적합함

### 10.3 ZSET 적용 방식

단순 누적 ZSET 하나만 쓰면 최근 7일 조건을 맞추기 어렵기 때문에 아래처럼 설계합니다.

- 일자별 ZSET 생성
- 예: `popular:menu:20260715`
- 주문 발생 시 해당 날짜 ZSET score 증가
- 최근 7일 조회 시 7개 ZSET을 합산해 top3 조회

### 10.4 트레이드오프

장점:

- 실시간 랭킹 처리 적합
- top N 조회 빠름

단점:

- 최근 7일 정확한 윈도우 처리 복잡
- 키 관리 비용 증가
- DB와 정합성 관리 필요

따라서 이번 과제에서는:

- 기본 구현은 DB 집계
- 확장 설계는 Redis ZSET

으로 나누는 것이 더 안전하다고 판단했습니다.

## 11. 캐싱 전략

### 11.1 적용 원칙

캐시는 `조회성 데이터`에만 적용하고, `정합성이 중요한 상태 데이터`에는 적용하지 않습니다.

### 11.2 캐시 대상

- 메뉴 목록 조회
- 인기 메뉴 조회
- 필요 시 메뉴 상세 조회

### 11.3 캐시 비대상

- 사용자 포인트 잔액
- 주문 상태
- Outbox 상태

### 11.4 캐시 정책

`Cache Aside` 전략을 사용합니다.

- 조회 시 캐시에 없으면 DB 조회 후 캐시에 저장
- 변경 발생 시 관련 캐시 무효화

TTL 예시는 아래와 같습니다.

- 메뉴 목록: 10분~30분
- 인기 메뉴: 1분~5분

### 11.5 예상 문제와 대응

문제:

- stale data
- 캐시 스탬피드
- 캐시 무효화 누락

대응:

- 짧은 TTL
- 변경 시 명시적 evict
- 인기 메뉴는 정답 소스를 DB로 유지

## 12. 메뉴 목록 조회 정책

### 12.1 왜 1페이지만 조회하는가

메뉴 목록 조회는 이번 과제에서 대규모 카탈로그 탐색이 핵심이 아니라고 판단했습니다.

또한 커피 메뉴는 보통 개수가 크지 않기 때문에 과도한 페이징 설계보다 `첫 페이지 중심 단순 조회`가 더 과제 범위에 맞다고 보았습니다.

이유는 아래와 같습니다.

- 과제 핵심이 메뉴 탐색 UX가 아니라 주문과 결제 정합성에 있음
- 메뉴 수가 상대적으로 적다고 가정 가능함
- 불필요한 복잡도를 줄이고 핵심 문제에 집중 가능함

확장 방향:

- 추후 메뉴 수가 많아지면 페이지네이션 추가
- 현재는 1페이지 조회 또는 전체 조회로 단순화

## 13. 인덱싱 전략

### 13.1 주요 조회 패턴

- 사용자 식별값으로 사용자 조회
- 사용자 포인트 지갑 조회
- 최근 7일 완료 주문 집계
- 메뉴별 주문 횟수 집계
- Outbox 미전송 이벤트 조회

### 13.2 계획 중인 인덱스

- `User(userIdentifier)` unique
- `PointWallet(userId)` unique
- `CoffeeOrder(status, orderedAt, menuId)`
- `CoffeeOrder(userId, orderedAt)`
- `OrderOutbox(status, createdAt)`

### 13.3 EXPLAIN 기반 검증 전략

인덱스는 추가만 하는 것이 아니라 실제 실행 계획을 확인합니다.

확인 항목:

- Full Table Scan 발생 여부
- Index Range Scan 여부
- rows 수
- key 사용 여부
- Extra 정보

### 13.4 인덱스의 한계와 대응

한계:

- 인덱스가 많아질수록 쓰기 성능 저하
- 복합 인덱스가 모든 조건을 완벽히 해결해주지는 않음
- group by, order by, range 조건이 동시에 복잡할 수 있음

대응:

- 핵심 조회 패턴 중심으로 최소 인덱스 구성
- `EXPLAIN` 결과 기반 조정
- 과한 선행 최적화는 지양

## 14. QueryDSL 고도화 전략

### 14.1 사용 목적

정적 메서드 이름 기반 조회는 조건이 조금만 늘어나도 한계가 있습니다.

특히 주문 검색, 관리자 조회, 인기 메뉴 집계 확장 시 동적 조건 조합이 필요할 수 있어 QueryDSL 적용을 고려하고 있습니다.

### 14.2 적용 후보

- 인기 메뉴 집계 조회
- 주문 이력 검색
- 관리자용 검색 필터 API 확장

### 14.3 적용 정책

- 단순 조회는 기본 JPA, JPQL 사용
- 복잡한 동적 조회만 QueryDSL 적용
- Custom Repository 계층으로 분리

### 14.4 기대 효과

- 동적 조건 확장성 확보
- 타입 세이프 쿼리 작성
- 가독성과 유지보수성 향상

## 15. 테스트 전략

### 15.1 테스트 목표

테스트는 단순 기능 확인이 아니라 아래를 검증하는 목적을 가집니다.

- 기능이 요구사항대로 동작하는지
- 동시 요청에서도 정합성이 유지되는지
- 이벤트 전송 실패 상황에서도 시스템이 안전한지
- 조회 결과와 집계 결과가 정확한지

### 15.2 단위 테스트

- 포인트 충전 성공, 실패
- 포인트 부족 주문 실패
- 판매 중지 메뉴 주문 실패
- 예외 처리
- 인기 메뉴 집계 로직

### 15.3 통합 테스트

- 주문 시 포인트 차감 + 주문 생성 + Outbox 저장이 함께 커밋되는지
- 주문 실패 시 rollback 되는지
- 캐시 무효화 동작
- Redis 락 연동 가능 여부

### 15.4 동시성 테스트

핵심 시나리오:

- 잔액 5000P에서 4000P 메뉴 2건 동시 주문
- 기대 결과: 1건 성공, 1건 실패, 최종 잔액 1000P

추가 시나리오:

- 주문과 충전 동시 요청
- 여러 스레드가 같은 사용자에게 동시에 주문 요청
- 최종 포인트 잔액과 주문 수가 일관된지 검증

### 15.5 Kafka, Outbox 테스트

- Outbox 저장 성공 여부
- Publisher 재시도
- Consumer 멱등 처리
- DLT 이동 여부

## 16. 부하 테스트 전략

### 16.1 왜 k6를 선택하는가

- HTTP API 부하 테스트에 적합함
- 스크립트 기반이라 시나리오 제어가 쉬움
- ramp-up, threshold, duration 설정이 직관적임
- 결과를 수치화해 설명하기 좋음

### 16.2 부하 테스트 대상

- 메뉴 목록 조회 API
- 인기 메뉴 조회 API
- 포인트 충전 API
- 주문, 결제 API

### 16.3 일반 부하 테스트

목적:

- 예상 사용량 범위에서 정상 동작 확인

기준:

- 동시 사용자 50~100명 수준

이유:

- 과제 규모에서 현실적인 혼잡 상황을 재현하기 적절함
- 너무 낮으면 병목이 드러나지 않고, 너무 높으면 인프라 한계만 먼저 보일 수 있음
- 주문 API, 락 대기, DB 커넥션 풀 반응을 보기 위한 초기 기준치로 적절함

### 16.4 한계 테스트

목적:

- 어느 지점부터 에러율이 증가하는지 확인

방식:

- 사용자 수를 점진적으로 증가시키며 병목 지점 탐색

### 16.5 급상승 테스트

목적:

- 짧은 시간에 요청이 급증할 때 안정적인지 확인

기준:

- 동시 사용자 10명에서 200명까지 급격히 증가

이유:

- 특정 시점에 주문이 몰리는 상황을 가정하기 위함
- 락 경합, 커넥션 풀 고갈, Kafka 적체, 응답 시간 급증 같은 병목을 빠르게 드러내기 위함
- 시스템의 회복력과 피크 대응 능력을 보기 위함

### 16.6 내구성 테스트

목적:

- 장시간 실행 시 자원 누수나 성능 저하 확인

방식:

- 30분~1시간 이상 지속 요청
- 응답 시간 증가, 메모리 사용량, 커넥션 풀 상태 관찰

### 16.7 주요 관찰 지표

- 평균 응답 시간
- p95, p99 응답 시간
- 에러율
- 처리량
- 락 대기 시간
- DB 커넥션 점유
- 중복 차감 발생 여부

## 17. HikariCP Connection Pool 전략

### 17.1 왜 중요한가

주문, 결제 API는 락과 트랜잭션을 함께 사용하기 때문에 DB 커넥션 풀 설정이 병목이 될 수 있습니다.

### 17.2 현재 범위에서의 판단

이번 과제에서는 HikariCP 튜닝 자체를 주요 구현 범위로 두지는 않았습니다.

현재 단계에서는 정합성 보장과 동시성 제어 구조를 먼저 안정적으로 구현하는 것이 우선이라고 판단했습니다.

다만, 락과 트랜잭션이 함께 사용되는 주문/결제 API 특성상 실제 트래픽이 증가하면 커넥션 풀 설정이 병목으로 이어질 수 있으므로, 이는 후속 성능 최적화 단계에서 반드시 확인해야 할 항목이라고 보고 있습니다.

### 17.3 후속 최적화 관점에서 보는 이유

향후 부하 테스트나 운영 환경에 가까운 검증을 진행하게 되면 아래 항목들을 점검할 필요가 있습니다.

- `maximumPoolSize`
- `connectionTimeout`
- `idleTimeout`
- `maxLifetime`

특히 아래와 같은 상황에서 HikariCP 튜닝 필요성이 커질 수 있다고 판단했습니다.

- 락 대기 중 커넥션 점유 시간이 길어지는 경우
- 주문 트랜잭션 수가 증가하면서 커넥션 풀이 빠르게 소진되는 경우
- DB 자체의 처리 한계보다 애플리케이션 커넥션 관리가 먼저 병목이 되는 경우

즉, 현재는 TODO 성격의 후속 최적화 항목으로 두되, 분산락·트랜잭션·비동기 이벤트 전송 구조가 자리잡은 이후 실제 병목 지점을 확인하면서 조정하는 것이 더 합리적이라고 판단했습니다.

## 18. 트레이드오프 정리

### 18.1 분산락 선택의 트레이드오프

장점:

- 다중 인스턴스 환경 제어 가능
- 사용자 단위 직렬화 가능
- DB 앞단에서 경쟁 완화 가능

단점:

- Redis 의존성 증가
- 락 운영 복잡도 증가
- Redis 장애 시 영향 큼

### 18.2 Kafka 선택의 트레이드오프

장점:

- 비동기 분리
- 병렬 소비
- 이벤트 확장성
- 고가용성 구조 설명 가능

단점:

- 운영 복잡도 증가
- 중복 소비, 재처리, DLT 설계 필요
- 과제 규모 대비 다소 무거울 수 있음

### 18.3 Outbox 선택의 트레이드오프

장점:

- DB와 이벤트 저장의 정합성 강화
- 이벤트 유실 위험 감소
- 재시도 가능

단점:

- 폴링 지연
- 테이블 정리 필요
- 추가 구현 비용 발생

### 18.4 Redis ZSET 선택의 트레이드오프

장점:

- 실시간 랭킹 처리 적합
- top N 조회 빠름

단점:

- 최근 7일 정확한 윈도우 처리 복잡
- DB와 정합성 관리 필요
