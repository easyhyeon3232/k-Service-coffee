# Code Convention

## 1. 목적

이 문서는 개인 프로젝트 `coffee`에서 일관된 기준으로 코드를 작성하기 위한 규칙을 정의한다.
특히 클래스와 메서드의 역할이 주석만으로도 빠르게 전달되도록 작성 기준을 맞추는 것을 목표로 한다.

## 2. 핵심 원칙

- 한 번에 이해되는 코드로 작성한다.
- 이름만 보고 역할을 알 수 있게 작성한다.
- 한 메서드는 한 가지 역할에 집중한다.
- 기능 개발과 구조 개선은 구분한다.
- 계층별 책임을 명확히 나눈다.

## 3. 프로젝트 구조 기준

프로젝트 구조는 계층 기준으로 나눈다.

예시:

```text
controller
service
repository
entity
dto
exception
config
```

기준은 다음과 같다.

- Controller: HTTP 요청과 응답 처리
- Service: 비즈니스 로직 처리
- Repository: DB 접근
- Entity: 영속성 객체
- DTO: 요청과 응답 데이터 전달
- Exception: 예외와 에러 코드 관리

## 4. 네이밍 규칙

### 4.1 클래스

- 클래스명은 명사로 작성한다.
- 역할이 드러나는 접미어를 사용한다.

예시:

- `OrderController`
- `PointService`
- `MenuRepository`
- `OrderCreateRequest`
- `ErrorCode`

### 4.2 메서드

- 메서드명은 동사로 시작한다.
- 이름만 보고 동작이 예상되어야 한다.

예시:

- `createOrder`
- `chargePoint`
- `findPopularMenus`
- `validateBalance`

### 4.3 변수

- 변수명은 역할 중심으로 작성한다.
- boolean 값은 `is`, `has`, `can`, `should`로 시작한다.
- 컬렉션은 복수형으로 작성한다.

예시:

- `remainingPoint`
- `popularMenus`
- `isSoldOut`

## 5. 코드 스타일 기준

- 기본 정렬과 포맷팅은 IDE 기본 설정을 우선 사용한다.
- 사람이 임의로 맞추기보다 IDE 포맷을 일관되게 적용한다.
- 한 줄이 너무 길어지면 의미 단위로 줄바꿈한다.
- 빈 줄은 논리 단위를 나누는 용도로만 사용한다.

## 6. 주석 작성 기준

### 6.1 클래스

- 클래스에는 JavaDoc으로 역할을 설명한다.
- 이 클래스가 무엇을 담당하는지 한눈에 알 수 있게 작성한다.

예시:

```java
/**
 * 커피 주문 생성과 주문 조회를 담당하는 서비스 클래스.
 */
public class OrderService {
}
```

### 6.2 메서드

- 메서드에는 다른 사람이 봐도 역할과 의도를 바로 이해할 수 있도록 주석을 작성한다.
- 단, 코드만 봐도 obvious한 설명은 피한다.
- 특히 분기 이유, 정책 이유, 예외 발생 이유를 남긴다.
- 모든 메서드에 기계적으로 주석을 달지 않는다.
- 단순 getter, setter, 단순 CRUD 위임 메서드는 이름으로 의도를 드러내는 것을 우선한다.
- 공개 메서드, 비즈니스 정책 메서드, 분기 많은 메서드에 우선적으로 주석을 작성한다.

좋은 예:

```java
// 포인트 부족 시 주문 자체를 막아야 하므로 차감 전에 선검증한다.
```

피해야 할 예:

```java
// 포인트를 차감한다.
```

## 7. 메서드 작성 기준

- 메서드는 가능하면 짧게 유지한다.
- 조건 분기가 깊어지면 메서드 분리를 먼저 검토한다.
- 검증, 계산, 저장, 변환 책임이 섞이면 분리한다.
- 파라미터가 많아지면 요청 객체로 묶을 수 있는지 검토한다.

비권장 예:

- 메뉴 조회, 포인트 검증, 주문 생성, 응답 변환을 한 메서드에서 모두 처리

## 8. 리팩터링 기준

- 기능 개발 중 구조 개선은 허용한다.
- 단, 기능 커밋과 리팩터링 커밋은 분리한다.
- 리팩터링은 동작 변경 없이 가독성과 책임 분리에 집중한다.
- 테스트가 있는 영역은 테스트 통과 상태를 유지한 채 정리한다.

우선 적용할 리팩터링 방식:

1. 이름 개선
2. 메서드 분리
3. 조건문 단순화
4. 중복 제거

## 9. 에러 처리 기준

에러 메시지는 문자열 하드코딩 대신 에러 코드를 상수로 관리한다.
실무에서 많이 쓰는 방식처럼 `ErrorCode` enum 또는 상수 클래스를 사용한다.

예시:

```java
public enum ErrorCode {
    USER_NOT_FOUND("USER_001", "사용자를 찾을 수 없습니다."),
    MENU_NOT_FOUND("MENU_001", "메뉴를 찾을 수 없습니다."),
    INSUFFICIENT_POINT("POINT_001", "포인트가 부족합니다."),
    INVALID_POINT_AMOUNT("POINT_002", "충전 금액은 0보다 커야 합니다.");

    private final String code;
    private final String message;
}
```

### 9.1 에러 코드 작성 기준

- 도메인별 prefix를 둔다.
- 숫자는 세 자리 정도로 통일한다.
- 코드와 메시지를 함께 관리한다.
- 사용자 메시지는 짧고 명확하게 작성한다.

예시:

- `USER_001`
- `MENU_001`
- `ORDER_001`
- `POINT_001`

### 9.2 메시지 톤

메시지 톤은 많이 사용하는 방식으로 아래처럼 통일한다.

- 짧고 명확하게 작성한다.
- 원인을 바로 알 수 있게 작성한다.
- 감정적인 표현은 사용하지 않는다.
- 책임 회피성 표현보다 상태 설명형 문장을 사용한다.

좋은 예:

- `사용자를 찾을 수 없습니다.`
- `판매 중인 메뉴만 주문할 수 있습니다.`
- `포인트가 부족합니다.`

피해야 할 예:

- `오류가 발생했습니다.`
- `잘못된 요청입니다.`
- `처리할 수 없습니다.`

## 10. 실무 기준

코드는 단순히 동작하는 것보다 정합성, 성능, 유지보수성을 함께 고려해서 작성한다.
특히 금액, 포인트, 주문, 재고처럼 값이 틀어지면 안 되는 도메인은 아래 기준을 우선 적용한다.

### 10.1 정합성 우선

- 포인트 차감, 주문 생성, 상태 변경처럼 데이터가 함께 맞아야 하는 작업은 정합성을 우선한다.
- 한쪽만 저장되고 다른 한쪽이 실패하는 구조를 피한다.
- 비즈니스적으로 반드시 함께 성공해야 하는 작업은 같은 트랜잭션 안에서 처리한다.

coffee 프로젝트 예시:

- 주문 생성과 포인트 차감은 하나의 트랜잭션으로 처리한다.
- 포인트만 차감되고 주문이 저장되지 않는 상황을 만들지 않는다.

### 10.2 트랜잭션 범위 명확화

- Service 레이어에서 트랜잭션 경계를 관리한다.
- Controller나 Repository에서 비즈니스 트랜잭션을 결정하지 않는다.
- 조회 전용 로직은 읽기 전용 트랜잭션을 고려한다.

기준:

- 쓰기 로직: `@Transactional`
- 조회 로직: 필요 시 `@Transactional(readOnly = true)`

### 10.3 N+1 방지

- 연관 엔티티 조회 시 반복 쿼리가 발생하지 않도록 주의한다.
- 목록 조회에서 연관 데이터가 함께 필요하면 `fetch join`, `EntityGraph`, DTO 조회를 우선 검토한다.
- 반복문 안에서 Repository를 다시 호출하는 구조를 피한다.

피해야 할 예:

```java
for (Order order : orders) {
    Menu menu = menuRepository.findById(order.getMenuId()).orElseThrow();
}
```

권장 예:

- 주문과 메뉴를 한 번에 조회하는 JPQL 작성
- 화면 응답에 맞는 DTO 프로젝션 조회

### 10.4 조회 성능 고려

- 필요한 컬럼만 조회한다.
- 단건 조회와 목록 조회를 구분한다.
- 집계가 필요한 경우 애플리케이션 메모리 계산보다 DB 집계를 우선 검토한다.
- 페이징이 필요한 목록은 전체 조회하지 않는다.

coffee 프로젝트 예시:

- 인기 메뉴는 최근 7일 주문 데이터를 DB에서 집계해 조회한다.
- 주문 목록 화면이 필요하면 엔티티 전체보다 응답 DTO 기준 조회를 우선 고려한다.

### 10.5 조회와 변경 책임 분리

- 조회 로직과 상태 변경 로직을 한 메서드에 과하게 섞지 않는다.
- 검증, 계산, 저장, 응답 변환이 모두 한 메서드에 있으면 분리한다.
- 읽기 흐름과 쓰기 흐름을 나눠야 문제 추적이 쉬워진다.

### 10.6 동시성 고려

- 여러 요청이 동시에 들어올 때 값이 깨질 수 있는지 먼저 생각한다.
- 포인트, 재고, 수량 같은 값은 동시성 충돌 가능성을 고려한다.
- 필요한 경우 비관적 락, 낙관적 락, 버전 컬럼 등을 검토한다.

coffee 프로젝트 예시:

- 같은 사용자가 동시에 여러 번 주문할 때 포인트가 음수가 되지 않도록 고려한다.
- 포인트 차감 로직은 동시 요청 상황에서도 정합성이 깨지지 않게 설계한다.

### 10.7 예외 처리 일관성

- 예외는 도메인 규칙 기준으로 명확하게 나눈다.
- 같은 상황에 대해 매번 다른 메시지나 다른 응답 형식을 사용하지 않는다.
- 비즈니스 예외와 시스템 예외를 구분한다.

예시:

- `MENU_NOT_FOUND`
- `INSUFFICIENT_POINT`
- `INVALID_ORDER_REQUEST`

### 10.8 하드코딩 최소화

- 상태값, 에러 코드, 정책 기준값은 상수 또는 enum으로 관리한다.
- 매직 넘버를 직접 코드에 반복해서 쓰지 않는다.

예시:

- 최근 인기 메뉴 기준 기간 `7일`
- 최대 조회 개수 `3개`
- 메뉴 상태 `SALE`, `SOLD_OUT`

### 10.9 테스트 가능한 구조 유지

- 메서드는 테스트 가능한 단위로 분리한다.
- 외부 의존성이 많은 로직은 인터페이스나 협력 객체로 분리해 테스트하기 쉽게 만든다.
- 정책성 로직은 private 안에 숨기기보다 의미 있는 메서드로 분리하는 것을 우선 검토한다.

### 10.10 로그 기준

- 장애 추적에 필요한 핵심 정보는 로그로 남긴다.
- 정상 흐름 전체를 과도하게 로그로 찍지 않는다.
- 사용자 식별값, 주문 ID, 에러 코드처럼 추적에 필요한 값 위주로 남긴다.

주의:

- 민감 정보는 로그에 남기지 않는다.
- 포인트, 주문 처리 실패 시 원인 파악 가능한 수준의 로그를 남긴다.

## 11. 테스트 기준

### 11.1 어떤 메서드를 테스트할지 판단하는 기준

이 메서드를 테스트해야 할까?

- 조건 분기가 있는가? `YES -> 테스트 필수`
- 계산 또는 변환 로직이 있는가? `YES -> 테스트 필수`
- 상태가 바뀌는가? `YES -> 테스트 권장`
- 단순 CRUD 위임인가? `YES -> 테스트 생략 가능`

### 11.2 테스트 생략 가능한 경우

- 단순 CRUD 위임
- Repository에 `findById`, `save`만 호출하는 경우
- JPA 기본 제공 메서드 호출만 있는 경우
- 프레임워크가 보장하는 동작만 검증하는 경우

예시:

- `repository.save(entity)`만 호출하는 단순 저장 메서드
- `findById` 결과를 그대로 반환하는 단순 조회 메서드

## 12. 테스트 케이스 설계 원칙

### 12.1 코드 작성 전에 자연어로 케이스를 먼저 도출한다

케이스 도출 순서:

1. 정상 케이스
2. 경계값 케이스
3. 예외 케이스

### 12.2 Given / When / Then 구조를 유지한다

```java
@Test
@DisplayName("보유 포인트가 주문 금액과 같으면 주문할 수 있다")
void create_order_when_point_equals_price_success() {
    // Given
    long currentPoint = 4000L;
    long menuPrice = 4000L;

    // When
    boolean result = orderService.canOrder(currentPoint, menuPrice);

    // Then
    assertThat(result).isTrue();
}
```

### 12.3 요구사항 키워드를 테스트 케이스로 변환한다

조건 키워드:

- `~이면`
- `~경우`
- `~이상`
- `~이하`
- `~초과`
- `~미만`

결과 키워드:

- `~해야 한다`
- `~불가능하다`
- `~반환한다`
- `~예외가 발생한다`

경계 키워드:

- `최소`
- `최대`
- `정확히`
- `초과`
- `미만`

## 13. coffee 프로젝트 기준 테스트 예시

### 13.1 포인트 충전

- 정상: 충전 금액이 1000원이면 포인트가 증가한다
- 경계: 충전 금액이 1원이면 충전된다
- 예외: 충전 금액이 0이면 예외가 발생한다
- 예외: 충전 금액이 음수면 예외가 발생한다

### 13.2 주문 생성

- 정상: 포인트가 가격보다 크면 주문이 생성된다
- 경계: 포인트가 가격과 정확히 같으면 주문이 생성된다
- 예외: 포인트가 가격보다 작으면 예외가 발생한다
- 예외: 존재하지 않는 메뉴면 예외가 발생한다
- 예외: 판매 중지 메뉴면 예외가 발생한다

### 13.3 인기 메뉴 조회

- 정상: 최근 7일 완료 주문 기준으로 상위 메뉴가 조회된다
- 경계: 정확히 7일 전 주문이 포함되는지 확인한다
- 예외: 주문 데이터가 없으면 빈 목록을 반환한다

## 14. 레이어별 테스트 전략

### 14.1 Service 레이어

목적: 비즈니스 로직 검증

사용 어노테이션:

- `@ExtendWith(MockitoExtension.class)`
- `@Mock`
- `@InjectMocks`

테스트할 것:

- 정상 동작
- 조건 분기
- 계산 또는 변환 로직
- 상태 변경
- 존재하지 않는 데이터
- 협력 객체 호출 여부

coffee 프로젝트 예시:

- 포인트 부족 시 주문 생성 예외
- 충전 후 포인트 증가
- 존재하지 않는 사용자 조회 시 예외
- 주문 저장 호출 여부 검증

### 14.2 Controller 레이어

목적: HTTP 인터페이스 검증

사용 어노테이션:

- `@WebMvcTest`
- `@MockBean`
- `@Autowired MockMvc`

테스트할 것:

- HTTP 상태코드
- 응답 Body 필드 존재 여부
- 필수 파라미터 누락 시 400 응답
- 예외가 올바른 HTTP 코드로 변환되는지

coffee 프로젝트 예시:

- 주문 생성 성공 시 `201`
- 존재하지 않는 메뉴 요청 시 `404`
- 충전 금액 누락 시 `400`
- 포인트 부족 예외가 적절한 에러 응답으로 내려오는지

테스트하지 않을 것:

- 비즈니스 로직 자체

### 14.3 Repository 레이어

목적: 커스텀 쿼리 정확성 검증

사용 어노테이션:

- `@DataJpaTest`

테스트할 것:

- 커스텀 JPQL 또는 QueryDSL
- 날짜 범위 조건 조회
- 상태 필터 조회
- 페이징
- fetch join
- 집계 쿼리
- 빈 결과 반환

coffee 프로젝트 예시:

- 최근 7일 완료 주문 기준 인기 메뉴 조회
- 판매 중인 메뉴만 조회
- 날짜 범위 주문 조회

테스트하지 않을 것:

- JPA 기본 제공 메서드 `save`, `findById`

## 15. 좋은 테스트 작성 기준

반드시 지켜야 하는 것:

- assert 없는 테스트 작성 금지
- `@DisplayName`은 한국어로 작성
- 테스트 하나에 케이스 하나만 검증
- 외부에서 보이는 결과를 기준으로 검증

### 15.1 assert와 verify 기준

- 반환값이 있는 경우 `assertThat` 우선 사용
- 반환값이 없고 호출 여부가 중요하면 `verify` 사용

### 15.2 경계값 케이스

경계값은 반드시 포함한다.

- 정확히 같은 값
- 초과 값
- 미만 값
- 최솟값
- 최댓값

## 16. 레이어 배치 판단 기준

| 테스트 케이스 | 레이어 | 이유 |
| --- | --- | --- |
| 포인트 부족 시 주문 생성 예외 발생 | Service | 비즈니스 규칙 |
| 주문 응답 Body에 orderId 필드 존재 | Controller | HTTP 응답 구조 |
| 최근 7일 인기 메뉴 조회 결과 정렬 확인 | Repository | 집계 쿼리 정확성 |
| 포인트 충전 후 잔액 증가 | Service | 상태 변경과 계산 로직 |
| 존재하지 않는 메뉴 요청 시 404 응답 | Controller | HTTP 상태코드 |

혼동하기 쉬운 기준:

- 비즈니스 규칙 예외 발생 여부는 `Service`
- 그 예외가 어떤 HTTP 코드로 내려가는지는 `Controller`

## 17. TDD 흐름

새 기능 개발 시 아래 순서를 따른다.

1. 요구사항에서 자연어 테스트 케이스 도출
2. 테스트 코드 작성
3. 테스트 실패 확인
4. 최소 구현으로 테스트 통과
5. 리팩터링

원칙:

- 테스트 파일을 먼저 만든다.
- 처음에는 실패하는 것이 정상이다.
- 테스트 통과 후 구조를 개선한다.
- 리팩터링 중에도 테스트 통과 상태를 유지한다.
