# Git Convention

## 1. 목적

이 문서는 개인 프로젝트 `coffee`에서 일관된 Git 이력과 작업 흐름을 유지하기 위한 규칙을 정의한다.
목표는 다음과 같다.

- 브랜치 이름만 봐도 작업 목적을 알 수 있다.
- 커밋 메시지만 읽어도 변경 의도를 이해할 수 있다.
- 기능 개발과 구조 개선 이력을 분리해서 추적할 수 있다.

## 2. 브랜치 전략

브랜치 구조는 아래 기준으로 운영한다.

```text
main <- dev <- feature/...
```

### 2.1 브랜치 역할

- `main`: 배포 기준 브랜치, 항상 안정적인 상태 유지
- `dev`: 개발 통합 브랜치, 기능 브랜치를 병합하는 기준 브랜치
- `feature/...`: 개별 기능 개발 브랜치

### 2.2 브랜치 생성 규칙

- 새로운 기능 개발은 항상 `dev`에서 분기한다.
- 기능 개발 완료 후 `feature/...`를 `dev`에 병합한다.
- 배포 또는 제출 가능한 시점에 `dev`를 `main`에 반영한다.

브랜치 이름 규칙:

- `feature/기능명`
- `fix/버그명`
- `refactor/대상명`
- `docs/문서명`
- `test/대상명`
- `chore/작업명`

브랜치 suffix는 자동 검증을 위해 영문 소문자, 숫자, 하이픈(`-`)만 사용한다.

예시:

- `feature/order-create`
- `feature/point-charge`
- `fix/point-validation`
- `refactor/order-service`

## 3. 기본 원칙

- 커밋은 하나의 의도만 담는다.
- 기능 개발 커밋과 리팩터링 커밋은 분리한다.
- 의미 없는 중간 저장 커밋은 남기지 않는다.
- `dev`에 병합하기 전 변경 파일을 직접 다시 읽는다.

## 4. 커밋 메시지 규칙

커밋 메시지는 한글로 작성한다.

형식:

```text
type: 변경 내용
```

예시:

```text
feat: 커피 주문 생성 기능 추가
fix: 포인트 부족 검증 누락 수정
refactor: 주문 생성 로직 메서드 분리
docs: 테스트 전략 문서 보완
test: 포인트 차감 경계값 테스트 추가
chore: 공통 예외 코드 상수 추가
```

## 5. 커밋 타입

사용 가능한 커밋 타입은 아래 6개로 제한한다.

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `docs`: 문서 수정
- `test`: 테스트 코드 추가 또는 수정
- `chore`: 설정, 빌드, 상수, 환경 정리 등 기타 작업

`style` 타입은 별도로 사용하지 않는다.
단순 정렬이나 포맷 수정은 관련 작업 커밋에 함께 포함하거나 필요 시 `chore`로 처리한다.

## 6. 커밋 메시지 작성 기준

- 제목은 짧고 명확하게 작성한다.
- 무엇을 바꿨는지 드러나게 작성한다.
- 한 커밋에 여러 성격이 섞이면 가장 핵심 목적 기준으로 작성한다.
- 제목 끝에 마침표를 붙이지 않는다.

좋은 예:

- `feat: 인기 메뉴 조회 API 추가`
- `fix: 존재하지 않는 메뉴 주문 시 예외 처리 수정`
- `refactor: 포인트 검증 메서드 분리`

피해야 할 예:

- `수정`
- `커밋`
- `feat: 이것저것 수정`

## 7. 커밋 단위 기준

좋은 커밋 단위 예시:

- 주문 생성 기능 추가
- 포인트 차감 경계값 테스트 추가
- 예외 코드 상수 정리
- 주문 서비스 메서드 분리

좋지 않은 커밋 단위 예시:

- 주문 기능 추가 + 포인트 리팩터링 + 테스트 수정
- 관련 없는 여러 도메인 수정
- 기능 수정과 정리 작업을 한 번에 포함

권장 순서:

1. 테스트 케이스 도출
2. 테스트 코드 작성
3. 기능 구현
4. 리팩터링
5. 문서 반영

## 8. 리팩터링 커밋 기준

기능 개발 중 구조 개선은 허용한다.
단, 아래 원칙을 지킨다.

- 기능 추가 커밋과 리팩터링 커밋은 분리한다.
- 리팩터링 커밋에서는 동작을 바꾸지 않는다.
- 리팩터링 전후 테스트 통과 상태를 유지한다.

예시 흐름:

```text
test: 주문 생성 실패 케이스 추가
feat: 주문 생성 기능 구현
refactor: 주문 서비스 검증 로직 분리
```

## 9. 병합 원칙

- `feature/...`는 `dev`로 병합한다.
- `dev`는 충분히 검증된 뒤 `main`으로 반영한다.
- 병합 전 최소한 아래를 확인한다.

1. 테스트 통과 여부
2. 불필요한 로그 제거 여부
3. 주석 처리된 코드 제거 여부
4. 커밋 메시지 가독성

## 10. 추천 작업 흐름

1. 요구사항 정리
2. `dev` 최신화
3. `feature/...` 브랜치 생성
4. 테스트 케이스 도출
5. 테스트 작성
6. 구현
7. 리팩터링
8. 커밋 정리
9. `dev` 병합
10. 최종 검증 후 `main` 반영

## 11. 자동 검증 범위

PR에서는 아래 항목을 자동 검증한다.

- 브랜치 이름 형식
- 브랜치 흐름 규칙
- 커밋 메시지 형식과 허용 타입

자동 검증은 `.github/scripts/validate_git_convention.py` 에서 수행한다.
