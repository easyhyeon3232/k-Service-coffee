# TIL - 주문 API 부하 테스트 실패 후 시나리오 보정으로 재검증한 과정

## 1. 문제 상황

`k6`로 주문 API 부하 테스트를 수행했을 때 아래 임계치를 통과하지 못했다.

- `p95 = 1.93s`
- `p99 = 3.09s`
- `http_req_failed = 64.62%`

처음에는 주문 API 자체가 부하를 견디지 못한 것처럼 보였다.

## 2. 왜 바로 성능 문제로 단정하면 안 되는가

이번 테스트는 같은 `memberId = 1`로 반복 주문을 보내는 방식이었다.

주문 API는 포인트를 차감하는 구조이기 때문에, 테스트가 진행될수록 해당 회원의 포인트가 빠르게 소진될 수 있다.
이 경우 `INSUFFICIENT_POINT` 같은 비즈니스 예외가 대량 발생하고, `k6`에서는 이런 응답도 실패로 집계된다.

즉 이번 실패율은 서버 장애만 반영한 값이 아니라, 비즈니스 실패가 함께 섞인 결과일 가능성이 높다.

## 3. 실제로 배운 점

- 조회 API와 달리 주문 API는 상태를 소비하는 API라서 테스트 데이터 준비가 매우 중요하다.
- 부하 테스트는 요청 수만 늘리는 것이 아니라, 테스트 대상 도메인의 특성을 함께 고려해야 한다.
- 실패율을 해석할 때는 4xx 비즈니스 실패와 5xx 서버 실패를 구분해야 한다.

## 4. 수정한 점

주문 부하 테스트 스크립트를 아래와 같이 보완했다.

- 테스트 시작 전 대상 회원에게 충분한 포인트를 자동 충전하도록 수정
- `MEMBER_IDS` 환경 변수를 통해 여러 회원으로 주문을 분산할 수 있도록 수정
- 사전 충전에 성공한 회원만 실제 주문 대상에 포함하도록 수정
- 매 반복마다 회원을 순환 선택해 특정 회원 1명에게만 부하가 몰리지 않게 수정

## 5. 수정 후 재실행 결과

수정 후 아래 명령어로 다시 테스트했다.

```bash
k6 run -e BASE_URL=http://localhost:8080 -e MEMBER_IDS=1,2,3 -e MENU_ID=1 -e ORDER_TEST_INITIAL_CHARGE=300000000 loadtest/k6/order-api.js
```

재실행 결과:

- `p95 = 229.95ms`
- `p99 = 652.42ms`
- `http_req_failed = 0.00%`
- 총 요청 수: `41,450`
- 실패 체크: `3건`

처음 실패했던 결과와 달리, 시나리오를 보정한 뒤에는 응답 시간과 실패율 기준을 모두 통과했다.

즉 문제의 핵심은 주문 API 구현 자체보다, 테스트 시나리오가 주문 도메인의 특성을 충분히 반영하지 못했던 점에 더 가까웠다.

## 6. 다음 테스트 방식

다음부터는 아래 방식으로 주문 부하 테스트를 진행한다.

1. `MEMBER_IDS=1,2,3`처럼 실제 존재하는 테스트 회원만 사용한다.
2. `setup()` 단계에서 각 회원에 충분한 포인트를 충전한다.
3. 주문 요청은 회원별로 분산한다.
4. 서버 로그를 함께 확인해 포인트 부족, 락 획득 실패, 서버 에러를 구분한다.
5. 혼합 부하 테스트에서는 인기 메뉴 조회 API를 함께 실행해 읽기/쓰기 혼합 상황도 본다.

## 7. 결론

이번 경험을 통해 부하 테스트는 단순히 트래픽을 많이 주는 작업이 아니라, 도메인 정책과 테스트 데이터 상태까지 함께 설계해야 의미 있는 결과를 얻을 수 있다는 점을 배웠다.

특히 주문처럼 상태를 소비하는 API는 테스트 데이터가 부족하면 성능 문제처럼 보이는 가짜 실패가 쉽게 생길 수 있다.
따라서 API 구현을 바로 의심하기보다, 테스트 시나리오를 먼저 점검하고 보정한 뒤 다시 측정하는 접근이 필요하다는 점을 확인했다.
